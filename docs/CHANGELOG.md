## Задача 5.2 — Промокоды в админке + полировка

- CRUD промокодов (ТЗ 6.4, только роль admin): `app/admin/promo_codes_router.py` + сервисные функции в `app/orders/service.py`. Код всегда приводится к верхнему регистру и проверяется на уникальность (409 `PROMO_CODE_EXISTS`); удаление промокода, который уже использовался (`used_count > 0`), запрещено (409 `PROMO_CODE_IN_USE`) — вместо удаления такой код деактивируется через `PATCH`. Frontend: `/admin/promo-codes` (создание, инлайн-редактирование размера скидки и активности, удаление), ссылка в навигации видна только роли admin.
- Найден и исправлен денежный баг (ТЗ 8, «целостность денег»): `compute_discount` не ограничивала процентную скидку сверху — промокод с `discount_value > 100%` мог дать скидку больше суммы заказа (отрицательный `total`). Для фиксированной скидки капирование уже было (`min(value, subtotal)`), для процентной — не было. Исправлено (капируется как и фиксированная); дополнительно на уровне БД добавлены `CHECK`-ограничения `ck_promo_codes_discount_value_positive` (> 0) и `ck_promo_codes_percent_discount_max_100` (процентная скидка ≤ 100%), чтобы такую строку нельзя было создать вообще — приложение проверяет то же самое раньше (422), чем дойдёт до БД.
- Сквозной проход по разделу 8 ТЗ:
  - **Rate limiting**: у `POST /orders` не было лимита, хотя ТЗ 5.5 явно требует 10 заказов/час/IP (логин и регистрация уже были лимитированы с Задачи 1.2). Добавлено; попутно вынесены общие `client_ip()`/`check_rate_limit()` в `core/rate_limit.py` (раньше были приватными копиями внутри `auth/router.py`) и переиспользованы в `orders/router.py`.
  - **CORS**: `settings.cors_origins_list` существовал с Задачи 0.2, но `CORSMiddleware` нигде не подключался — реальный баг, не проявлявшийся локально, так как весь трафик браузера идёт same-origin через Caddy. Подключено в `main.py` (`allow_credentials=True` — обязательно для cookie с refresh-токеном при кросс-origin сценариях).
  - **Security-заголовки**: добавлены в `caddy/Caddyfile` (единая точка входа и для API, и для фронта) — `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, `Permissions-Policy`, `Strict-Transport-Security` (на голом `:80` в деве браузер эту последнюю просто игнорирует без TLS — заработает бесплатно, когда Задача 5.3 даст Caddy настоящий домен).
  - **Аудит логов**: у переходов статуса заказа (`orders/service.py::transition_status`) и у платёжных webhook'ов (`payments/service.py`) не было ни одного лога, хотя ТЗ 8 требует INFO на каждый переход/webhook — добавлены. `payments/service.py` заодно переведён со stdlib `logging` на `structlog` (был единственным местом в кодовой базе на голом `logging`, из-за чего PrintLoggerFactory‑логи не попадали в общий JSON-конвейер). `user_id` теперь привязывается к контексту structlog в `get_optional_user` (`app/dependencies.py`) один раз на запрос — появляется во всех логах запроса, включая `request_finished`, без протаскивания через каждый вызов сервиса. Чтобы это можно было проверить через `caplog` (а не только `capture_logs`), логирование переведено на `structlog.stdlib.LoggerFactory()` — теперь любой structlog-вызов идёт и через обычный `logging`, а не только в stdout.
  - Frontend: `not-found.tsx`, `error.tsx` + `global-error.tsx`, `sitemap.ts` (категории и товары, постранично через реальный `/products`) + `robots.ts` (закрыты `/admin`, `/cart`, `/checkout`, `/login`), сгенерированные `icon.tsx`/`opengraph-image.tsx`-заглушки HobbyLife (старый дефолтный `favicon.ico` от `create-next-app` удалён), `metadataBase` в корневом layout (нужен, чтобы `opengraph-image` резолвился в абсолютный URL).

Исправлено тем же приёмом: данные оборачиваются в try/catch с пустым fallback (статические страницы каталога всё равно попадают в sitemap, категории/товары просто не добавляются на этапе сборки — сам `sitemap.xml` не закэширован статически насовсем, реальный трафик подхватит их). Проверено локальным `npm run build` без доступного бэкенда и отдельным `docker build ./frontend`.

## Задача 5.1 — Excel-импорт

- `app/imports/`: интерфейс `ImportSource` (`sources/base.py`, единственный метод `parse(bytes) -> list[ParsedImportRow]`) + `XlsxImportSource` (openpyxl) — абстракция намеренно выделена уже сейчас, чтобы будущий источник 1С/CommerceML (ТЗ 11.2, v2, не реализуется в этой задаче) подключался без изменений в логике upsert.
- Модель строки = вариант товара; строки группируются по `(Название, external_id)` в один товар с несколькими вариантами. Двухуровневый upsert (собственная трактовка неоднозначной формулировки ТЗ, т.к. у товара нет SKU): товар ищется/обновляется по `external_id`, вариант — по `SKU` (оба поля уже были `UNIQUE` с Задачи 1.1). Категория (`Хранение и уборка/Вёдра`) резолвится по пути через `/`, недостающие уровни создаются автоматически с автогенерацией слага (`python-slugify` + числовой суффикс при коллизии).
- Эндпоинты 6.4 (`app/admin/imports_router.py`, только роль admin): `POST /admin/imports/xlsx` (загрузка + предпросмотр первых 20 строк со счётчиками создание/обновление/ошибки), `POST /admin/imports/{id}/apply` (ставит фоновую arq-задачу `apply_import_job`), `GET /admin/imports/{id}` (статус/отчёт), `GET /admin/imports/template` (скачиваемый xlsx-шаблон).
- Применение импорта (`apply_import`) — каждая товарная группа оборачивается в свой try/except с `session.rollback()` при ошибке: одна сломанная группа не прерывает остальной импорт (прямое требование DoD). Фото из колонки «Фото» (список URL через запятую) скачиваются и заливаются в S3 только для НОВЫХ товаров (не при обновлении — `ProductImage` не хранит исходный URL, чтобы дедуплицировать при повторном импорте того же файла), дальше переиспользуется тот же воркер ресайза 400/800px webp из Задачи 2.2. Битые/недоступные URL фото пропускаются без падения строки.
- Frontend: `/admin/imports` (только роль admin, ссылка в навигации тоже только для admin) — выбор файла → загрузка и предпросмотр (таблица первых 20 строк + счётчики) → «Применить импорт» → поллинг статуса каждые 1.5 с (тот же паттерн `refetchInterval`, что и на странице статуса заказа из Задачи 3.3) → итоговый отчёт (создано/обновлено/ошибок + ссылка на скачивание xlsx-отчёта об ошибках); отдельная кнопка «Скачать шаблон». Добавлен `apiFetchRaw` в `shared/api/client.ts` (как `apiFetch`, но не навязывает `Content-Type: application/json` и отдаёт сырой `Response`) — нужен для multipart-загрузки файла и скачивания бинарного xlsx с тем же токеном авторизации.
- Найдено и исправлено до мёржа:
  - Реальный баг порядка роутов FastAPI/Starlette: `GET /admin/imports/template` был объявлен ПОСЛЕ `GET /admin/imports/{import_id}`, из-за чего строка «template» скармливалась в `{import_id}: uuid.UUID` и падала с 422 — маршруты матчатся в порядке регистрации, а не по специфичности. Исправлено переносом статического маршрута выше параметризованного.

Исправлено пересборкой (`docker compose up -d --build`), тот же класс проблемы, что раньше был с `npm install` фронтенда.

## Задача 4.1 — Платёжный контур + MockPaymentProvider

- Интерфейс `PaymentProvider` (`app/payments/providers/base.py`): `create_payment(order) -> PaymentInfo`, `parse_webhook(request) -> ParsedWebhookEvent` (сама проверяет подпись, кидает `PaymentWebhookError` при неудаче), `refund(payment, amount)`. Реестр провайдеров (`providers/registry.py`) собирается из `PAYMENT_PROVIDERS` в конфиге — сейчас там только `mock`.
- `MockPaymentProvider`: `create_payment` отдаёт URL `http://{DOMAIN}/api/v1/payments/mock/{id}/page` (обязательно через Caddy, а не внутренний хост — тот же класс бага, что с presigned S3-URL в Задаче 2.3); страница — две формы «Оплатить»/«Отклонить» с заранее подписанными (HMAC-SHA256, секрет из `PAYMENT_WEBHOOK_SECRET`) скрытыми полями, отправляющие POST прямо на `/api/v1/webhooks/payment/mock` — буквально «нажатие шлёт подписанный webhook самому себе». Доп. поле `return_url` в форме — редирект браузера на `/checkout/success|fail/{number}` после обработки; серверные вызовы webhook (без этого поля) получают обычный JSON-ответ.
- Webhook `POST /v1/webhooks/payment/{provider}` по алгоритму 5.4: неверная подпись → 400 `INVALID_WEBHOOK_SIGNATURE`; идемпотентность через `payment_events` (provider, event_id) — повторная доставка того же события не переобрабатывается; сверка суммы — при несовпадении с `order.total` платёж помечается `failed` и пишется ERROR-лог, заказ не трогается; при `succeeded` — тяжёлая часть (перевод заказа в `paid`, эта же функция ставит email в очередь) уносится в фоновую задачу `process_payment_succeeded`, сам webhook отвечает быстро.
- `refund_payment` (`app/payments/service.py`): вызывает `provider.refund()`, помечает платёж `refunded` и переводит заказ в `refunded` через существующий автомат (Задача 3.2). HTTP-эндпоинт админки для возврата — по-прежнему Задача 4.2 (ТЗ 6.4), здесь только сервисная функция с тестом.
- `orders/service.create_order`: провизорная заглушка `payment_url` из Задачи 3.2 заменена на настоящий вызов `provider.create_payment(order)` — онлайн-заказ теперь получает реальную (рабочую) ссылку на оплату.
- Тесты (5 новых, `tests/test_payments_webhook.py`): успешная оплата (через настоящий HTTP webhook + фоновая задача) переводит заказ в `paid`; двойная доставка одного и того же события обрабатывается один раз (проверено по списку задач в очереди — второй раз ничего не ставится); неверная подпись → 400, платёж не тронут; несовпадение суммы → платёж `failed` + пойман ERROR-лог (`caplog`); возврат меняет статус и платежа, и заказа.
- Проверено вручную: полный цикл через настоящий браузер и настоящий контейнер `worker` (не тестовая привязка сессии) — checkout с `payment_method=online` → переход на страницу `/api/v1/payments/mock/{id}/page` → клик «Оплатить» → редирект на `/checkout/success/{number}` → заказ реально в статусе `paid` при повторном запросе.

## Задача 3.3 — Frontend: корзина и checkout

- Корзина (`/cart`, CSR): TanStack Query как единственный источник состояния корзины (место зustand-заглушки из Задачи 2.3 — счётчик в шапке теперь настоящий, через тот же `useCartQuery`). Все мутации (добавление на карточке товара, изменение количества/удаление на странице корзины, очистка) — оптимистичные с откатом при ошибке (ТЗ 7.3: обязательно для корзины); применение промокода — без оптимизма (скидка percent/fixed заранее неизвестна фронту, ждём реальный ответ). Предупреждения по каждой позиции — «товар закончился» / «доступно только N шт.» из `is_available`/`available_qty`; отдельного предупреждения об изменении цены нет и не нужно — бэкенд и так всегда отдаёт актуальную цену (Задача 3.1), устаревшей просто не бывает.
- Checkout (`/checkout`, одна страница, форма с zod-валидацией): контакты → способ доставки (тариф курьера и порог бесплатной доставки — с бэка, `GET /v1/checkout/config`, новый маленький эндпоинт) → адрес (если курьер) → способ оплаты (список доступных — тоже с бэка, `cash_on_delivery` всегда, `online` только если сконфигурированы провайдеры) → комментарий → «Оплатить». После создания заказа: есть `payment_url` → редирект на него; нет (`cash_on_delivery`) → редирект на `/checkout/success/{number}`. Ошибки оформления (`OUT_OF_STOCK`, `EMPTY_CART`, `DELIVERY_ADDRESS_REQUIRED`, ...) показываются прямо на форме — их сообщения уже человекочитаемые на русском (бэкенд, Задача 3.2), отдельный маппинг кодов не понадобился.
- `/checkout/success/[number]` и `/checkout/fail/[number]`: поллинг `GET /orders/{number}?email=` раз в 3 с до 2 минут (ТЗ 7.1 п.5 — webhook платёжки может прийти позже редиректа); статус и сумма показываются, как только приходят.
- Тесты (Playwright, `frontend/e2e/`, запускаются локально против поднятого `docker compose` стека — отдельного CI-джоба не заводили, т.к. `test-backend` поднимает только postgres+redis, а e2e нужен весь стек с Caddy/frontend/minio, это отдельное расширение CI-архитектуры за рамками фронтенд-задачи): каталог → товар → корзина → checkout (`cash_on_delivery`) → страница успеха с номером заказа; конкурирующий покупатель (отдельная сессия) через прямые API-запросы выкупает весь остаток раньше — оформление в браузере получает 409 с сообщением «Некоторые товары недоступны в нужном количестве» прямо на форме.
- Проверено вручную в браузере (Playwright-скрипт, не сохранён): полный проход каталог → товар → добавить в корзину → корзина → checkout → страница успеха; мобильная раскладка 360px (`/cart`, `/checkout`) без горизонтального скролла; прод-сборка (`docker build ./frontend`, без живого бэкенда) — `/cart` и `/checkout` статические, результатные и каталожные страницы динамические, как и ожидалось.

## Задача 3.2 — Оформление заказа и конечный автомат

- `POST /orders` — оформление строго по алгоритму 5.2 одной транзакцией: читает снапшот корзины из Redis, атомарно списывает остаток по каждой позиции (`UPDATE ... WHERE stock_qty >= :qty AND is_active`, проверка rowcount — под конкуренцией на последнюю единицу товара проходит ровно один запрос, остальные получают `OUT_OF_STOCK` со списком недоступных позиций), пересчитывает цены/промокод/доставку из БД (клиентские цены полностью игнорируются — их даже нет в схеме запроса), генерирует номер `ORD-{YYYYMMDD}-{счётчик}` через атомарный Redis-счётчик, очищает корзину. Ветвление по `payment_method` (5.4): `cash_on_delivery` — сразу `processing`, без `awaiting_payment`; `online` — `awaiting_payment` + `expires_at = +30 мин` и создание `Payment` (реальный провайдер/`payment_url` — Задача 4.1; сейчас строка платежа создаётся, а `payment_url` временно указывает только на неё).
- Доставка: курьер обязателен с адресом (иначе `DELIVERY_ADDRESS_REQUIRED`), бесплатна от `FREE_DELIVERY_THRESHOLD`, иначе `COURIER_DELIVERY_COST`; самовывоз всегда бесплатный.
- Сервис переходов статусов (`orders/service.transition_status`) — полный автомат 5.1, каждый неразрешённый переход → 409 `INVALID_STATUS_TRANSITION`; переход в `cancelled`/`refunded` возвращает остатки по всем позициям заказа; переход в `paid`/`shipped`/`cancelled` ставит письмо в очередь (arq). История — `order_status_history` при каждой смене.
- Фоновая крон-задача (`arq`, раз в минуту): отменяет просроченные `awaiting_payment` (`expires_at` в прошлом) через тот же сервис переходов — остатки возвращаются автоматически.
- Личный кабинет 6.3: `GET/PATCH /me`, `GET/POST /me/addresses`, `PATCH/DELETE /me/addresses/{id}` (новый модуль `app/account/`); `GET /me/orders`, `GET /me/orders/{number}`, `POST /me/orders/{number}/cancel` (только из `pending`/`awaiting_payment`, иначе `ORDER_NOT_CANCELLABLE`) — в `app/orders/`. Гостевой статус заказа: `GET /orders/{number}?email=` — не палит существование заказа при несовпадении email (единый `ORDER_NOT_FOUND`).
- Рефактор: `_promo_validation_error`/`_compute_discount` из Задачи 3.1 стали публичными `validate_promo`/`compute_discount` в `app/cart/service.py`, плюс новый `get_cart_snapshot()` — оформление заказа переиспользует их вместо дублирования логики промокода.
- Тесты (34 новых): конкурентное оформление последней единицы товара через `asyncio.gather` двух НЕЗАВИСИМЫХ сессий (не общий `db_session`/`client` — там одна транзакция на тест, а для настоящей проверки блокировки строки нужны два реальных пересекающихся соединения) — проходит ровно один, остаток = 0, создан ровно один заказ; таймаут возвращает остатки (сценарий через крон-функцию напрямую); каждый из 8 запрещённых переходов автомата → 409; итоги пересчитаны из БД (изменение цены варианта между добавлением в корзину и оформлением отражается в заказе; подсунутая в теле запроса цена не влияет); списание/оплата при получении/бесплатная и платная доставка; промокод в заказе и инкремент `used_count`; email-задачи в очереди для paid/shipped/cancelled и НЕ ставятся для остальных переходов; гостевой и личный доступ к заказам, включая отсутствие утечки чужих заказов; CRUD адресов с эксклюзивностью `is_default`.

## Задача 3.1 — Корзина

- Корзина на Redis: hash `cart:{cart_id}` (гость) / `cart:user:{user_id}` (залогиненный), TTL 30 дней, продлевается при каждой мутации; `cart_id` — UUID в httpOnly cookie, назначается при первом обращении. Промокод хранится отдельным служебным полем в том же hash (не может коллизировать с variant_id-ключами, так как не является UUID).
- Эндпоинты 6.1: `GET /cart`, `POST /cart/items`, `PATCH /cart/items/{variant_id}` (0 = удалить), `DELETE /cart`, `POST /cart/promo`. Лимиты из 5.3: максимум 50 позиций, максимум 99 шт. на позицию.
- Ответ корзины всегда пересчитывается из БД: актуальная цена, `is_available`/`available_qty` по каждой позиции (не блокирует и не подменяет количество в самой корзине — это ответственность фронта показать предупреждение, а окончательное принудительное применение остатков — на оформлении заказа в Задаче 3.2). Промокод валидируется заново при каждом чтении корзины (активность, срок действия, `min_order_total`, лимит использований) — если промокод перестал быть валиден, скидка перестаёт применяться, но сам код в корзине не стирается.
- При логине (`/auth/login`) — слияние гостевой корзины (по cookie `cart_id`) в пользовательскую: количества суммируются и капаются остатком на складе (`stock_qty`); позиция, у которой остаток обнулился, из объединённой корзины выпадает. Гостевая корзина удаляется после слияния.
- `app/dependencies.py`: `get_current_user` разложен на `get_optional_user` (возвращает `None` при отсутствии заголовка, но всё ещё падает 401 на невалидный/просроченный токен) + `get_current_user`, оборачивающий его для случаев, где авторизация обязательна — так корзина может обслуживать и гостя, и залогиненного пользователя одной и той же зависимостью.
- Обнаружено и обойдено при разработке: несколько команд redis-py (`hgetall`, `hset`, `hdel`) типизированы для async-клиента как `Awaitable[T] | T` (а не чисто `Awaitable[T]`, в отличие от `get`/`set`/`expire`/`delete`, которые типизируются нормально) — mypy strict корректно ловит `await` над невсегда-awaitable типом. Обойдено тремя точечными обёртками с `# type: ignore[misc]` в одном месте (`app/cart/service.py`), а не россыпью игнор-комментариев по всем вызовам.
- Тесты (20 новых, `tests/test_cart.py`): добавление/увеличение/лимит 99/лимит 50 позиций/неизвестный вариант; PATCH установка и удаление через `qty=0`; очистка корзины; деактивированный и закончившийся на складе вариант → `is_available=false`; промокоды — процентный и фиксированный (не уходит в минус), не найден, неактивен, истёк, ещё не начался, `min_order_total` не набран, исчерпан лимит использований; слияние гость+юзер через реальный `/auth/login` с капом по остаткам и очисткой гостевой корзины после.

- `TimestampedBase` (`app/database.py`): общие `id UUID PK`, `created_at`/`updated_at` для всех таблиц.
- SQLAlchemy-модели (13 таблиц): `users`, `refresh_tokens`, `addresses` (auth); `categories`, `products`, `product_variants`, `product_images` (catalog); `orders`, `order_items`, `order_status_history`, `promo_codes` (orders); `payments`, `payment_events` (payments) — с CHECK/UNIQUE-ограничениями и индексами из раздела 4 ТЗ, полем `external_id` из 11.1.
- Единая миграция: расширения `citext` и `pg_trgm`; `search_vector` (GENERATED tsvector + GIN) и GIN trgm-индекс на `products.name`; общий триггер `set_updated_at()` (на `clock_timestamp()`) на всех 13 таблицах. Upgrade/downgrade проверены с нуля.
- `tests/factories.py`: фабрики factory_boy на все 13 моделей (build-стратегия; FK передаёт вызывающий тест после `flush()` родителя).
- Seed-скрипт (`make seed`, `app/scripts/seed.py`): 3 категории, 10 товаров HobbyLife, 27 вариантов (объём 0.5/1/1.5 л, цвета); идемпотентен (пропускает, если каталог уже заполнен).
- Тесты на каждое CHECK-ограничение (users.role, orders.status/delivery_method/payment_method, product_variants.price/stock_qty, order_items.quantity, payments.status, promo_codes.discount_type), на UNIQUE(product_id, options), на генерацию search_vector и на срабатывание триггера updated_at.
