## Корзина и чекаут блокируют оформление недоступных товаров заранее

Вопрос: «почему товар, которого нет в наличии, можно заказать и оформить?». Проверил напрямую через API (создал тестовый товар с `stock_qty=0`, добавил в корзину, вызвал `POST /v1/orders`) — заказ на бэкенде реально создать нельзя, `create_order` уже атомарно проверяет остаток на каждую позицию и возвращает `409 OUT_OF_STOCK` до создания заказа (плюс это уже было покрыто тестами, включая гонку за последнюю единицу). Проблема была не в том, что заказ проходит, а в том, что фронтенд не мешал дойти до этого 409 — можно было спокойно перейти в чекаут, заполнить всю форму и только на кнопке «Оплатить» получить отказ.

- **`CartView.tsx`**: `hasUnavailableItems` (уже вычислялся, но раньше использовался только для мягкого предупреждения) теперь на самом деле блокирует переход к оформлению — кнопка/ссылка «Оформить заказ» (и в сайдбаре, и в мобильной sticky-панели) при недоступном товаре в корзине превращается в задизейбленную некликабельную кнопку вместо `<Link href="/checkout">`.
- **`CheckoutForm.tsx`**: та же проверка продублирована на странице оформления (защита в глубину — остаток мог обнулиться уже после перехода на `/checkout`, до отправки формы) — кнопка «Оплатить» дизейблится, и рядом появляется понятное сообщение со ссылкой обратно в корзину, вместо того чтобы полагаться только на позднюю ошибку от бэкенда.
- e2e-тест `checkout.spec.ts` (`a competing checkout draining stock...`) обновлён под новое, более честное поведение: раньше он кликал «Оплатить» и ждал 409 с сервера, теперь конкурентная покупка того же остатка уже видна при обычной загрузке `/cart` и `/checkout` — тест проверяет, что на обеих страницах кнопка задизейблена и есть понятное сообщение, без необходимости реально отправлять форму.
- `tsc --noEmit`, `eslint .`, `next build` (все 30 маршрутов) — чисто. Живой e2e-прогон через Playwright не запускался — в этом окружении нет Chrome (тот же пробел, что и во всех предыдущих записях этого файла).

## Правки после ревью v2: бегущая строка в админке, поиск, дефолтный адрес

Три точечные правки по свежесделанному редизайну и одна маленькая, но реальная фича.

- **Бегущая строка теперь управляется из админки, не захардкожена.** До этого `PromoMarquee` показывал три жёстко зашитых в код пункта. Добавлено по образцу баннеров (тот же CRUD + drag-reorder + вкл/выкл, только без картинки и расписания — просто текст): модель `PromoMessage` (`text` пришлось переименовать в `message` — колонка `text` в теле класса перекрывает импортированную `sqlalchemy.text`, из-за чего `server_default=text("0")` на следующей же строке падал с `TypeError: 'MappedColumn' object is not callable`), публичный `GET /promo-messages`, админские `GET/POST/PATCH/DELETE /admin/promo-messages` + `PATCH /admin/promo-messages/reorder`, новый раздел «Бегущая строка» в админке. `PromoMarquee` переведён с клиентского компонента на `async`-серверный (как `Footer`/`HomePage`) — если админ ничего не настроил, показываются те же три честных факта по умолчанию (бесплатная доставка от порога, оплата при получении, самовывоз/доставка), так что полоса никогда не пустая на свежем магазине.
- **Убрана рамка/подсветка, всплывавшая в поле поиска товаров при клике** (`Header.tsx`) — было: постоянная 2px-рамка бренда плюс `focus-within:ring`, который добавлял вторую рамку поверх при фокусе и выглядел неряшливо. Оставлена только постоянная рамка, без изменения при фокусе.
- **Первый адрес пользователя теперь автоматически становится основным.** В `account/service.py::create_address` раньше `is_default` нужно было выставлять явно, даже для самого первого адреса — а по факту он один, других вариантов нет. Если у пользователя ещё нет ни одного адреса, `is_default` принудительно выставляется в `True` независимо от того, что пришло в запросе.
- Тесты: 6 новых в `test_admin_promo_messages.py` (CRUD, reorder + отказ при несовпадающем списке ID, публичный листинг видит только активные и в правильном порядке, 404 на несуществующее сообщение, 401/403 для не-admin); 1 новый в `test_account.py` (первый адрес — дефолтный без явного запроса, второй — не крадёт дефолт без явного запроса). `pytest tests/test_account.py tests/test_admin_promo_messages.py tests/test_admin_catalog.py` — 34/34. Полный `pytest -q` — 9 несовпадений, все того же класса пред-существующей проблемы с dev-данными/гонками с фоновым `worker`, что и в предыдущей записи (включая один новый флейк `test_payments_webhook.py::test_duplicate_webhook_delivery_processed_once`, воспроизведённый и подтверждённый прогоном в одиночку — проходит; ни один из изменённых в этой правке файлов платежей не касается). `ruff`/`mypy --strict` по бэкенду, `tsc --noEmit`/`eslint .`/`next build` (все 30 маршрутов, включая новый `/admin/promo-messages`) по фронтенду — чисто.
- Баннеры (`/admin/banners`) уже были полностью настраиваемы из админки до этой правки — заголовок, подзаголовок, ссылка, кнопка, фото, расписание, порядок, вкл/выкл; в этой задаче не менялись, только подтверждено при ответе на вопрос в чате.

## Точное воспроизведение дизайна: Стайл-тайл v2 (промо) + Главная v2

Импорт из Claude Design (`Style-tile с палитрой и компонентами`, файлы `HobbyLife Стайл-тайл v2 (промо).dc.html` и `HobbyLife Главная v2 (промо).dc.html`) — смена фирменной гаммы сторефронта с холодной синей на тёплую оранжево-красную «промо»-тему и полный редизайн главной страницы под неё. Мокап читался целиком (включая мобильную раскладку и dc-скрипт с данными компонентов) перед реализацией.

- **Токены дизайн-системы** (`app/globals.css`): `--color-brand` `#2F5AF5` → `#FF6A00`, `--color-brand-text` (текстовый безопасный вариант, WCAG AA) → `#C2410C` (сырой `#FF6A00` даёт только ~2.9:1 на белом), `--color-brand-soft` → `#FFF7F0`. `--color-accent-sale` (уже существовавший токен для скидок/бейджей — тот же смысловой слот, что и в мокапе) `#FF6A4D` → `#E3170A`, `--color-accent-sale-700` → `#C21308` (совпадает с hover-состоянием кнопок в самом мокапе). `--color-success` не менялся — `#1AA35A` уже совпадал с мокапом день в день. Ретема — по сути смена значений 5 CSS-переменных, а не точечная правка компонентов: `text-brand`/`bg-brand`/`text-accent-sale` и т.д. используются в 55 файлах сторefronта, и все они уже были на токенах, ни одного захардкоженного hex не нашлось (кроме служебной палитры цветов-свотчей товаров, не относящейся к бренду).
- **Админка осознанно не тронута** — в задаче явно попросили менять только сторефронт. `admin/layout.tsx`'s обёртка получила класс `.admin-shell`, который в `globals.css` жёстко фиксирует исходные синий/коралловый токены (и светлую, и тёмную тему админки) поверх новых сторefront-дефолтов — один явный, задокументированный якорь вместо бы точечных правок по всем 11 файлам админки, что используют `brand`.
- **Главная страница** (`app/(shop)/page.tsx`) переверстана под структуру мокапа: промо-полоса с бегущей строкой (новый виджет `PromoMarquee`, рендерится в `(shop)/layout.tsx` над шапкой), шапка (`Header.tsx`) — логотип с иконкой-плашкой, сплошная оранжевая кнопка «Каталог», поисковая строка с постоянной оранжевой рамкой и кнопкой «Найти»; hero-карусель (как была, просто перекрашена), панель «Товары дня», сетка иконок категорий, сетка «Скидки», карусель «Хиты продаж» (как была), плитки категорий с фото, полоса доверия. Футер (`Footer.tsx`) — 4 колонки вместо трёх строк текста.
- **Честные решения** (мокап предполагал больше, чем можно честно подкрепить реальными данными):
  - **Таймеры и полосы «осталось X из Y» убраны полностью.** В мокапе у каждого товара в «Товарах дня» — обратный отсчёт и шкала дефицита («осталось 7 из 32»). Ни то, ни другое не подкреплено реальными данными: у акций по товарам нет дедлайна (`compare_at_price` — это просто «была/стала», без срока), а «выделено на акцию N штук» нигде не считается и не резервируется. Вместо выдумки — только то, что уже честно есть: `discount_percent`/`compare_at_price` (реальные, считаются на лету в `catalog/service.py`) через уже существующий `ProductCard`, без всякой точечной доработки — бейдж скидки и зачёркнутая цена там уже были. Секции «Товары дня» и «Скидки» используют уже существующий и полностью реальный фильтр `GET /v1/products?on_sale=true` (backend уже был готов, просто не использовался на главной) — не пришлось ни трогать бэкенд, ни выдумывать сортировку.
  - **Плитки категорий с фото — добавлено реальное поле, не подделка.** В мокапе плитка категории — с фоновым фото товаров. У `Category` в БД не было поля для фото вообще. Добавлено по образцу `Banner` (тот же S3-пайплайн с фоновым ресайзом через arq): миграция `categories.image_s3_key`/`image_thumbnail_s3_key`, `POST /admin/categories/{id}/image`, новая фоновая задача `process_category_image` (300/800px превью+картинка, дешевле баннерных 400/1920, т.к. плитка — это половина ~1280px-контейнера, а не hero на всю ширину), поле `image_url` в публичном дереве категорий, посчитанное в `_build_category_tree` и закешированное в Redis на 300с — presigned URL живёт 3600с, так что кеш всегда обновится раньше, чем ссылка протухнет. Категория без загруженного фото — не подделка, просто тёплая плашка с иконкой категории вместо фото. Заодно из плитки убраны выдуманные в мокапе описание категории, скидка-бейдж и «от N сом» — ни одно из этих трёх полей не существует как реальные данные на уровне категории.
  - **Футер — контакты и информационные страницы оставлены как в мокапе, по прямой просьбе.** Телефон, WhatsApp/Telegram/Instagram и ссылки «Доставка и оплата»/«Возврат»/«Оптовым клиентам»/«Контакты» — таких страниц и контактов в проекте пока нет; заказчик попросил сделать пока с мок-данными мокапа один в один, поменяют сами позже. Реальные данные в футере — только ссылки раздела «Каталог» (настоящие категории верхнего уровня) и копирайт.
  - **Промо-полоса (бегущая строка) — только честные пункты.** У мокапа было 4 пункта, включая «скидки до -30% — только N дня» (подразумевает срок акции, которого нет) и адрес склада на Ошском рынке (нигде не сконфигурирован). Оставлены три реальных: бесплатная доставка от `free_delivery_threshold` (тот же конфиг, что использует форма чекаута), оплата при получении, самовывоз/доставка по Бишкеку (оба способа доставки реальны).
  - **Полоса доверия (4 факта)** — тоже только проверяемое: бесплатная доставка от порога (конфиг), оплата при получении (реальный способ оплаты), «остаток виден сразу» (реальная фича карточки товара — не выдумка), возврат/обмен (без конкретного числа дней — такой политики нигде не сконфигурировано). Не стали копировать мокаповское «пищевой пластик» — это сертификационное заявление о материале, которое нечем подтвердить на уровне кода.
- Тесты (backend, 2 новых в `test_admin_catalog.py`): загрузка фото категории появляется и в админском, и в публичном дереве категорий (после инвалидации кеша); отказ загрузки не-картинки с кодом `INVALID_IMAGE`, тем же, что и у баннеров. `pytest tests/test_admin_catalog.py tests/test_admin_images.py tests/test_email.py tests/test_orders_checkout.py` — 50/50 прошли (файлы, которых касалась эта задача). ## Транзакционные письма через Resend API (замена SMTP-заглушки)

В проекте уже была черновая заготовка отправки писем через SMTP (`aiosmtplib`, `SMTP_*` в `.env`) — по факту нерабочая (реальный SMTP никогда не настраивался ни в деве, ни в проде, см. запись «личный кабинет покупателя» ниже: «SMTP не настроен в деве, письмо реально не уходит»). Заменена целиком на Resend REST API (`https://api.resend.com/emails`), SMTP убран без остатка (код, зависимость, переменные окружения).

- **Конфигурация**: `SMTP_*` в `config.py`/`.env.example` заменены на `resend_api_key`/`email_from` (`RESEND_API_KEY`, `EMAIL_FROM=HobbyLife <onboarding@resend.dev>`). До верификации домена `hobbylife.kg` в Resend (SPF/DKIM — отдельная, более поздняя задача) отправка возможна только с `onboarding@resend.dev` и только на email, привязанный к самому аккаунту Resend — это ограничение задокументировано в `.env.example` и `docs/DEPLOY.md`, а после верификации меняется одна строка в `.env`, без правок кода.
- **`app/core/email.py` переписан заново**: `render_email_template(name, **ctx)` (Jinja2, `app/templates/emails/`, `select_autoescape`) + `async def send_email(to, subject, html)` — один POST на `https://api.resend.com/emails`, без ретраев (это не платёжный вебхук, идемпотентность не нужна). Ошибки (не-2xx ответ Resend и транспортные `httpx.HTTPError`) логируются как `resend_send_failed` с телом ответа/текстом ошибки и не пробрасываются дальше — фоновая arq-задача не падает, если Resend недоступен или отклонил письмо. Вызывается только из `app/workers/tasks.py`, никогда синхронно из HTTP-хендлера — регистрация/чекаут не ждут ответа Resend.
- **Шаблоны** (`app/templates/email/` → `app/templates/emails/`, все на русском, с текстовым лого «HobbyLife»): `verify_email.html` (подтверждение регистрации, ссылка с токеном, TTL 24 ч), `reset_password.html` (сброс пароля, TTL 1 ч), `order_status_update.html` (смена статуса заказа — номер, что изменилось, ссылка на статус заказа), и новый `set_password.html` (установка пароля для гостевого заказа).
- **Найдена и закрыта реальная дыра, не только заглушка по SMTP**: для гостевого чекаута (ТЗ 4: `password_hash` может быть `NULL`) не было вообще никакого способа задать пароль на созданный без него аккаунт — заказ оформлялся, аккаунт неявно заводился, а письма «установите пароль» не существовало ни как шаблона, ни как задачи. Проверка кода показала, что это не проверялось нигде: ни в `create_category`/`update_category`, ни в Excel-импортёре — админ (через `/admin/categories` или через импорт с длинным путём `"A/B/C/D"`) мог создать сколь угодно глубокое дерево категорий.

- `app/catalog/service.py`: `create_category` и `update_category` теперь считают итоговую глубину перед применением — `409 CATEGORY_TOO_DEEP`, если получится больше 3 уровней. При смене родителя учитывается не только сама категория, но и высота её поддерева (если `X` уже имеет собственного потомка, переместить `X` под категорию 3-го уровня нельзя — иначе потомок окажется на 5-м).
- `app/imports/service.py`: `_resolve_category_path` отклоняет путь длиннее 3 сегментов (`422 CATEGORY_TOO_DEEP`) — как и остальные ошибки построчной валидации, это не ломает весь импорт, а попадает в отчёт об ошибках для конкретной группы строк.
- Тесты (5 новых): создание ровно на 3 уровня — успешно; 4-й уровень — `409`; перемещение категории с потомком под категорию 3-го уровня — `409` (регрессия именно на «косвенное» превышение глубины через поддерево); Excel-импорт с 4-сегментным путём категории — ошибка попадает в отчёт, остальные строки импортируются как обычно.
- Проверено на полностью пересобранном стенде (`docker compose down -v` → `up --build` → `make migrate` → `make seed` → `make test` (200 прошли, 4 пропущены) → `make lint`) и вручную через реальные HTTP-запросы: 3 уровня создаются, 4-й отклоняется с точным кодом ошибки.

- Checkout (`/checkout`, одна страница, форма с zod-валидацией): контакты → способ доставки (тариф курьера и порог бесплатной доставки — с бэка, `GET /v1/checkout/config`, новый маленький эндпоинт) → адрес (если курьер) → способ оплаты (список доступных — тоже с бэка, `cash_on_delivery` всегда, `online` только если сконфигурированы провайдеры) → комментарий → «Оплатить». После создания заказа: есть `payment_url` → редирект на него; нет (`cash_on_delivery`) → редирект на `/checkout/success/{number}`. Ошибки оформления (`OUT_OF_STOCK`, `EMPTY_CART`, `DELIVERY_ADDRESS_REQUIRED`, ...) показываются прямо на форме — их сообщения уже человекочитаемые на русском (бэкенд, Задача 3.2), отдельный маппинг кодов не понадобился.
- `/checkout/success/[number]` и `/checkout/fail/[number]`: поллинг `GET /orders/{number}?email=` раз в 3 с до 2 минут (ТЗ 7.1 п.5 — webhook платёжки может прийти позже редиректа); статус и сумма показываются, как только приходят.
- Тесты (Playwright, `frontend/e2e/`, запускаются локально против поднятого `docker compose` стека — отдельного CI-джоба не заводили, т.к. `test-backend` поднимает только postgres+redis, а e2e нужен весь стек с Caddy/frontend/minio, это отдельное расширение CI-архитектуры за рамками фронтенд-задачи): каталог → товар → корзина → checkout (`cash_on_delivery`) → страница успеха с номером заказа; конкурирующий покупатель (отдельная сессия) через прямые API-запросы выкупает весь остаток раньше — оформление в браузере получает 409 с сообщением «Некоторые товары недоступны в нужном количестве» прямо на форме.
- Проверено вручную в браузере (Playwright-скрипт, не сохранён): полный проход каталог → товар → добавить в корзину → корзина → checkout → страница успеха; мобильная раскладка 360px (`/cart`, `/checkout`) без горизонтального скролла; прод-сборка (`docker build ./frontend`, без живого бэкенда) — `/cart` и `/checkout` статические, результатные и каталожные страницы динамические, как и ожидалось.

## Задача 3.2 — Оформление заказа и конечный автомат

- `POST /orders` — оформление строго по алгоритму 5.2 одной транзакцией: читает снапшот корзины из Redis, атомарно списывает остаток по каждой позиции (`UPDATE ... WHERE stock_qty >= :qty AND is_active`, проверка rowcount — под конкуренцией на последнюю единицу товара проходит ровно один запрос, остальные получают `OUT_OF_STOCK` со списком недоступных позиций), пересчитывает цены/промокод/доставку из БД (клиентские цены полностью игнорируются — их даже нет в схеме запроса), генерирует номер `ORD-{YYYYMMDD}-{счётчик}` через атомарный Redis-счётчик, очищает корзину. Ветвление по `payment_method` (5.4): `cash_on_delivery` — сразу `processing`, без `awaiting_payment`; `online` — `awaiting_payment` + `expires_at = +30 мин` и создание `Payment` (реальный провайдер/`payment_url` — Задача 4.1; сейчас строка платежа создаётся, а `payment_url` временно указывает только на неё).
- Доставка: курьер обязателен с адресом (иначе `DELIVERY_ADDRESS_REQUIRED`), бесплатна от `FREE_DELIVERY_THRESHOLD`, иначе `COURIER_DELIVERY_COST`; самовывоз всегда бесплатный.
- Сервис переходов статусов (`orders/service.transition_status`) — полный автомат 5.1, каждый неразрешённый переход → 409 `INVALID_STATUS_TRANSITION`; переход в `cancelled`/`refunded` возвращает остатки по всем позициям заказа; переход в `paid`/`shipped`/`cancelled` ставит письмо в очередь (arq). История — `order_status_history` при каждой смене.
- Фоновая крон-задача (`arq`, раз в минуту): отменяет просроченные `awaiting_payment` (`expires_at` в прошлом) через тот же сервис переходов — остатки возвращаются автоматически.
- Личный кабинет 6.3: `GET/PATCH /me`, `GET/POST /me/addresses`, `PATCH/DELETE /me/addresses/{id}` (новый модуль `app/account/`); `GET /me/orders`, `GET /me/orders/{number}`, `POST /me/orders/{number}/cancel` (только из `pending`/`awaiting_payment`, иначе `ORDER_NOT_CANCELLABLE`) — в `app/orders/`. Гостевой статус заказа: `GET /orders/{number}?email=` — не палит существование заказа при несовпадении email (единый `ORDER_NOT_FOUND`).
- Рефактор: `_promo_validation_error`/`_compute_discount` из Задачи 3.1 стали публичными `validate_promo`/`compute_discount` в `app/cart/service.py`, плюс новый `get_cart_snapshot()` — оформление заказа переиспользует их вместо дублирования логики промокода.
- Тесты (34 новых): конкурентное оформление последней единицы товара через `asyncio.gather` двух НЕЗАВИСИМЫХ сессий (не общий `db_session`/`client` — там одна транзакция на тест, а для настоящей проверки блокировки строки нужны два реальных пересекающихся соединения) — проходит ровно один, остаток = 0, создан ровно один заказ; таймаут возвращает остатки (сценарий через крон-функцию напрямую); каждый из 8 запрещённых переходов автомата → 409; итоги пересчитаны из БД (изменение цены варианта между добавлением в корзину и оформлением отражается в заказе; подсунутая в теле запроса цена не влияет); списание/оплата при получении/бесплатная и платная доставка; промокод в заказе и инкремент `used_count`; email-задачи в очереди для paid/shipped/cancelled и НЕ ставятся для остальных переходов; гостевой и личный доступ к заказам, включая отсутствие утечки чужих заказов; CRUD адресов с эксклюзивностью `is_default`.

## Задача 3.1 — Корзина

- Корзина на Redis: hash `cart:{cart_id}` (гость) / `cart:user:{user_id}` (залогиненный), TTL 30 дней, продлевается при каждой мутации; `cart_id` — UUID в httpOnly cookie, назначается при первом обращении. Промокод хранится отдельным служебным полем в том же hash (не может коллизировать с variant_id-ключами, так как не является UUID).
- Эндпоинты 6.1: `GET /cart`, `POST /cart/items`, `PATCH /cart/items/{variant_id}` (0 = удалить), `DELETE /cart`, `POST /cart/promo`. Лимиты из 5.3: максимум 50 позиций, максимум 99 шт. на позицию.
- Ответ корзины всегда пересчитывается из БД: актуальная цена, `is_available`/`available_qty` по каждой позиции (не блокирует и не подменяет количество в самой корзине — это ответственность фронта показать предупреждение, а окончательное принудительное применение остатков — на оформлении заказа в Задаче 3.2). Промокод валидируется заново при каждом чтении корзины (активность, срок действия, `min_order_total`, лимит использований) — если промокод перестал быть валиден, скидка перестаёт применяться, но сам код в корзине не стирается.
- При логине (`/auth/login`) — слияние гостевой корзины (по cookie `cart_id`) в пользовательскую: количества суммируются и капаются остатком на складе (`stock_qty`); позиция, у которой остаток обнулился, из объединённой корзины выпадает. Гостевая корзина удаляется после слияния.
- `app/dependencies.py`: `get_current_user` разложен на `get_optional_user` (возвращает `None` при отсутствии заголовка, но всё ещё падает 401 на невалидный/просроченный токен) + `get_current_user`, оборачивающий его для случаев, где авторизация обязательна — так корзина может обслуживать и гостя, и залогиненного пользователя одной и той же зависимостью.
- Обнаружено и обойдено при разработке: несколько команд redis-py (`hgetall`, `hset`, `hdel`) типизированы для async-клиента как `Awaitable[T] | T` (а не чисто `Awaitable[T]`, в отличие от `get`/`set`/`expire`/`delete`, которые типизируются нормально) — mypy strict корректно ловит `await` над невсегда-awaitable типом. Обойдено тремя точечными обёртками с `# type: ignore[misc]` в одном месте (`app/cart/service.py`), а не россыпью игнор-комментариев по всем вызовам.
- Тесты (20 новых, `tests/test_cart.py`): добавление/увеличение/лимит 99/лимит 50 позиций/неизвестный вариант; PATCH установка и удаление через `qty=0`; очистка корзины; деактивированный и закончившийся на складе вариант → `is_available=false`; промокоды — процентный и фиксированный (не уходит в минус), не найден, неактивен, истёк, ещё не начался, `min_order_total` не набран, исчерпан лимит использований; слияние гость+юзер через реальный `/auth/login` с капом по остаткам и очисткой гостевой корзины после.

## Задача 1.1 — Модели БД и миграции

- `TimestampedBase` (`app/database.py`): общие `id UUID PK`, `created_at`/`updated_at` для всех таблиц.
- SQLAlchemy-модели (13 таблиц): `users`, `refresh_tokens`, `addresses` (auth); `categories`, `products`, `product_variants`, `product_images` (catalog); `orders`, `order_items`, `order_status_history`, `promo_codes` (orders); `payments`, `payment_events` (payments) — с CHECK/UNIQUE-ограничениями и индексами из раздела 4 ТЗ, полем `external_id` из 11.1.
- Единая миграция: расширения `citext` и `pg_trgm`; `search_vector` (GENERATED tsvector + GIN) и GIN trgm-индекс на `products.name`; общий триггер `set_updated_at()` (на `clock_timestamp()`) на всех 13 таблицах. Upgrade/downgrade проверены с нуля.
- `tests/factories.py`: фабрики factory_boy на все 13 моделей (build-стратегия; FK передаёт вызывающий тест после `flush()` родителя).
- Seed-скрипт (`make seed`, `app/scripts/seed.py`): 3 категории, 10 товаров HobbyLife, 27 вариантов (объём 0.5/1/1.5 л, цвета); идемпотентен (пропускает, если каталог уже заполнен).
- Тесты на каждое CHECK-ограничение (users.role, orders.status/delivery_method/payment_method, product_variants.price/stock_qty, order_items.quantity, payments.status, promo_codes.discount_type), на UNIQUE(product_id, options), на генерацию search_vector и на срабатывание триггера updated_at.

## Задача 0.3 — CI и тестовый контур

- GitHub Actions (`.github/workflows/ci.yml`): `lint` (ruff, mypy, eslint, tsc), `test-backend` (postgres+redis сервисами, автоприменение миграций, pytest), `build` (сборка api и frontend образов).
- `tests/conftest.py`: `db_session` — транзакция с откатом (SAVEPOINT) после каждого теста; `client` — httpx-клиент против реального приложения с подменённым `get_db`; автоприменение Alembic-миграций перед тестовым сеансом.
- `tests/factories.py`: заготовка на factory_boy (`BaseFactory`, локаль `ru_RU`) для фабрик моделей в Задаче 1.1.
- Тесты на транзакционный откат (доказывают, что коммит внутри теста реально отменяется) и на фикстуру `client`; тесты `core/storage.py` пропускаются (не падают), если S3/MinIO недоступен — соответствует тому, что CI поднимает только postgres+redis.

## Задача 0.2 — Скелет backend-приложения

- `app/config.py` (pydantic-settings), `app/database.py` (async engine/session/`get_db`/`Base`), `app/exceptions.py` (`DomainError` + единый формат ошибок для всех исключений, включая встроенные HTTP/422).
- Request ID middleware + structlog JSON-логи (`request_id` в каждом логе запроса, заголовок `X-Request-ID`).
- `core/redis.py`, `core/storage.py` (S3-клиент на boto3, presigned URL, работает с MinIO).
- Alembic (async template), первая пустая миграция (upgrade/downgrade проверены с нуля).
- Пустые пакеты-заготовки для auth/catalog/cart/orders/payments/admin/workers.
- Тесты на всю новую функциональность (config, database, exceptions, middleware, redis, storage) — 12 тестов зелёные; ruff/mypy проходят.
