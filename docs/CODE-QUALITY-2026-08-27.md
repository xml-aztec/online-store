## 3. Эффективность запросов и производительность

**✅ N+1 не найден ни в одном из проверенных списочных эндпоинтов.** Реальное SQL-логирование на живом Postgres, реальные HTTP-запросы через Caddy:

| Эндпоинт | SQL-запросов на 1 HTTP-запрос | Комментарий |
|---|---|---|
| `GET /api/v1/products?page_size=20` | 5 | matching_ids, paginated select, батч-загрузка images по IN, facet price-range, facet options |
| `GET /api/v1/admin/orders?page_size=20` | 3 | auth lookup, count, paginated select — без обращения к relationships |
| `GET /api/v1/me/favorites?page_size=20` (5 избранных) | 5 | один батч-запрос `product_id IN (...)` на все 5 товаров, не 5 отдельных |
| `GET /api/v1/products/{slug}` | 5 | `selectinload` images/variants/category — по одному запросу на коллекцию |
| `GET /api/v1/products/{slug}/reviews` | 3 | `JOIN reviews+users`, автор не отдельным запросом |

Ключевое доказательство: число запросов **не растёт** с числом строк в списке — реальный лог на `/me/favorites` показывает один `SELECT ... WHERE products.id IN ($15,$16,$17,$18,$19)`, не пять последовательных. `catalog/service.py:387-454` (`hydrate_product_list_items`) и `:363-384` (`_load_images_by_product`) спроектированы под батч-загрузку сознательно.

**⚠️ Индексы: реальный пробел в миграциях, не проявляющийся на текущих данных.** `EXPLAIN ANALYZE` на реальном SQL из лога (каталог с фильтром по категории, admin-заказы с `status IN (...) ORDER BY created_at DESC`) — оба дают `Seq Scan`, не `Index Scan`. **Но** на 12-27 строках в таблице это ожидаемое и корректное поведение планировщика (Seq Scan на такой малой таблице дешевле) — само по себе не значит «индексы не работают», объём данных для этой проверки был слишком мал. Независимо от объёма данных подтверждён реальный пробел: `grep -rn "op.create_index" backend/alembic/versions/*.py` не находит ни одного индекса на `orders.status`, `orders.created_at` или `products.category_id` — при том что это единственные колонки в `WHERE`/`ORDER BY` этих двух самых частых запросов (подтверждено `\d orders`/`\d products` в psql — только `orders_pkey`/`orders_number_key` и, у products, `id`/`search_vector` GIN/`name` GIN trgm/`slug`/`external_id`). Каталожный полнотекстовый поиск получил продуманные индексы, а `category_id`-фильтр и `admin/orders`-список — нет. Не влияет на текущую производительность, станет проблемой при росте таблицы заказов.

**✅ Прод-сборка фронтенда — без аномалий.** `npm run build` (Next.js 16.2.12, Turbopack): `✓ Compiled successfully in 3.2s`. У этой версии Next.js Turbopack не печатает классическую таблицу route/size (`frontend/AGENTS.md` прямо предупреждает о breaking changes) — размеры взяты напрямую из `.next/static/chunks`: всего 1.6MB raw / 50 файлов, два самых тяжёлых чанка — `react-dom` (232KB raw/72KB gzip, framework runtime) и общий чанк `zod`-схем (292KB raw/67KB gzip) — оба ожидаемо тяжёлые и общие. `lucide-react` — 40 файлов импортируют именованно (`import { AlertCircle }`), ни одного `import *` — дерево-шейкинг работает. `qrcode` используется в одном файле (`admin/profile/page.tsx`) и не тянется в общие чанки — изолирован в отдельном 28KB чанке своего маршрута. Это не логическая ошибка в бизнес-коде — сама фича (статистика/баннеры/Telegram) работает верно, ломается именно проверка «ровно это множество», написанная в предположении чистой БД. Тесты используют `db_session` с транзакционным откатом (`create_savepoint`), но читают данные через HTTP-эндпоинты, которые видят реальные строки из общей dev-БД — тот же корневой механизм, что и раньше, теперь задевающий больше модулей просто потому, что их стало больше.
